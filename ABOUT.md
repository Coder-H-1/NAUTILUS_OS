# OVERVIEW

NAUTILUS_OS is a custom 64-bit bare-metal operating system (AArch64) built specifically for the Raspberry Pi 3 Model B+ v1.2. It aims to provide low-level learning regarding memory, I/O handling, and core OS functionalities. The OS currently features an HDMI-based framebuffer for text output, a rudimentary shell, primitive FAT32 parsing, USB keyboard input parsing, exception handling for system calls (via SVC), and basic process control block structures. It leverages Rust's `no_std` ecosystem to avoid the standard library and operates directly on hardware registers.

# WORKFLOW

1. **Boot Process**: The system boots from the SD card using `bootcode.bin` and `start.elf` which load the `kernel8.img` generated by this project.
2. **Initialization**: The boot code begins execution at the `_start` assembly routine, which sets up the stack pointer and halts secondary CPU cores. It then transfers execution to the `rust_main` function.
3. **Driver Loading**: In `kernel_main`, the system initializes essential hardware drivers: Clock, Timer, Memory, HDMI (framebuffer via mailbox), and USB stack (including keyboard and mass storage).
4. **Subsystems**: Next, kernel systems like the exception vector table (`vbar_el1`) and primitive process management structures are initialized.
5. **Interactive Shell**: Finally, execution enters an infinite loop in the interactive shell (`OS> `), reading scancodes from the USB keyboard and drawing characters on the screen via the HDMI framebuffer. A basic command `echo` is supported.

# ABOUT PROJECT

The primary focus of this project is learning systems programming by writing drivers and kernel components from scratch in Rust. Its initial intent was to run custom automated "scripts" from an external USB drive to control GPIO pins (as detailed in `SCRIPT.md`). Currently, the system supports reading basic user inputs to a shell and rendering them to a monitor, while keeping the structural framework open for multitasking and a virtual filesystem.

# WHAT IT USES

- **Language**: Rust (`#![no_std]`, `#![no_main]`).
- **Target**: `aarch64-unknown-none`.
- **Dependencies**: `font8x8` for rendering glyphs on the framebuffer.
- **Toolchain**: `llvm-tools-preview` and `cargo-binutils` for object copying to binary image `kernel8.img`.
- **Hardware**: Raspberry Pi 3 B+ v1.2 (Broadcom BCM2837 SoC).

# HOW IT COMMUNICATES AND INTERACTS

- **HDMI Output**: Communication with the GPU is done via the **Mailbox property interface**. The OS constructs a message (MailboxBuffer), writes its physical address to the mailbox register, and polls until the GPU acknowledges it. This retrieves a pointer to a framebuffer in memory where the OS directly writes pixel data (using `font8x8`) to draw characters.
- **User Input**: Interactions are handled via the USB protocol. A basic polling mechanism on the USB Host Controller (DWC2) detects keyboard attachment, retrieves scancodes, and converts them to ASCII for the shell.
- **Hardware Register I/O**: Direct memory-mapped I/O using `read_volatile` and `write_volatile` to MMIO base `0x3F00_0000` (for timers, mailbox, etc.) and `0x3F20_0000` (for GPIO).
- **System Calls**: Processes in user mode (EL0) use the `SVC` instruction to trap into the kernel (EL1). The exception handler intercepts the SVC trap, parses the `TrapFrame`, reads the syscall number from register `x8`, and maps it to an internal system function.

# WHAT EACH FILE DOES & HOW IT WORKS

### src/main.rs
- **What it does**: Entry point.
- **How it works**: Embeds global assembly `_start` to initialize CPU core 0 stack pointer, put other cores to sleep (WFE), and branch to `rust_main`, which calls `kernel_main`.

### src/kernel/main.rs
- **What it does**: Initializes drivers and kernel systems.
- **How it works**: Calls `init()` functions across drivers and components, then enters the `shell::start()` loop.

### src/kernel/vector.S
- **What it does**: Defines AArch64 exception vector table.
- **How it works**: Specifies 16 `ventry` points. Low EL AArch64 sync exceptions save the 31 registers (TrapFrame) onto the stack and call the Rust `sync_handler`.

### src/kernel/exception.rs
- **What it does**: Installs the vector table and handles traps.
- **How it works**: Uses `asm!` to write the address of `vector_table` into `vbar_el1`. Evaluates `esr` to determine if a trap was an SVC instruction and hands it to `syscall.rs`.

### src/kernel/process.rs
- **What it does**: Defines data structures for context switching.
- **How it works**: Holds `TrapFrame`, `Context`, and `ProcessControlBlock`. Includes an inline assembly function `switch_to_user` that uses `eret` to drop from EL1 to EL0 (User Mode).

### src/kernel/syscall.rs
- **What it does**: Resolves system calls.
- **How it works**: Reads `tf.regs[8]` for the syscall ID. Resolves basic stubs like `SYS_EXIT` (1) and `SYS_WRITE` (2).

### src/driver/hdmi.rs
- **What it does**: Setup framebuffer and draw text.
- **How it works**: Prepares a 36-word array requesting physical display size (1024x768), 32-bit depth, and a framebuffer pointer. Once the Mailbox grants it, it writes raw 24-bit/32-bit pixel data directly into RAM using a Scale2x algorithm against `font8x8` arrays.

### src/driver/gpio.rs
- **What it does**: Modifies pin logic levels.
- **How it works**: Uses Bitwise operations on Memory-Mapped I/O registers: `GPFSEL0` (Mode), `GPSET0` (High), `GPCLR0` (Low), and `GPLEV0` (Read).

### src/driver/mailbox.rs
- **What it does**: Generic Mailbox wrapper.
- **How it works**: Handles polling `MAILBOX_STATUS` for `MAILBOX_FULL` (writing) and `MAILBOX_EMPTY` (reading) to interact with the VideoCore IV GPU.

### src/driver/timer.rs
- **What it does**: Tracks system time.
- **How it works**: Reads the `TIMER_CLO` and `TIMER_CHI` MMIO registers of the BCM2837 System Timer for microsecond precision delays.

### src/driver/usb/*
- **What it does**: Custom lightweight USB Stack.
- **How it works**: Manipulates the DWC2 controller to enumerate devices (hubs, keyboards, mass storage). 

### src/fs/fat32.rs & src/fs/vfs.rs
- **What it does**: Reads disk layout.
- **How it works**: Reads Master Boot Record (MBR) Block 0 of a BlockDevice, locates Partition 1, evaluates the BIOS Parameter Block (BPB) to locate Root Directory and FAT tables for LBA offsets.

### src/core/shell.rs
- **What it does**: Minimal CLI.
- **How it works**: Blocks waiting for `get_key()`, echoes characters via `Hdmi::draw_char`, checks buffers against commands like `echo`, and prints responses.

# WHAT PROJECT IS DESIGNED TO DO TILL NOW

Till now, the project acts as a single-tasking, EL1 bare-metal loop. It can initialize hardware, draw an interactive terminal to a 1024x768 HDMI display, capture USB keyboard strokes, parse FAT32 partition metadata from a mass-storage device, and define standard data structures for User Mode processes and System Calls (though multitasking is not actively scheduling yet).

# WHAT THE OS IS DESIGNED TO DO TILL NOW

The OS was ultimately designed to execute an infinite loop of custom GPIO toggling based on `.txt` script payloads placed on a USB Mass Storage drive (as defined in `SCRIPT.md`). However, it has evolved slightly into an interactive shell environment for debugging and reading inputs, serving as a playground for foundational OS primitives.

# WHAT WE CAN ADD TO IT

To fully reach the intended goal and expand into a modern microkernel:
1. **Script Parser Engine**: An interpreter to parse the text files (e.g., `pin 7 inf > + 1 - 2`) from FAT32 and convert them into scheduled `timer::delay` and `gpio::set_pin` callbacks.
2. **Timer Interrupts**: Enable ARM generic timers and route them to `irq_handler` in `vector.S` to support asynchronous delays instead of synchronous `spin_loop` blocks.
3. **Process Scheduler**: Implement a Round-Robin scheduler in `process.rs` to allow multiple scripts to execute concurrently via timer interrupts, saving context to `TrapFrame`.
4. **Memory Management**: Implement paging and an MMU driver to map virtual memory to physical addresses and provide memory protection (malloc/free allocators).
5. **Complete FAT32 Integration**: Complete `read_file` in `fat32.rs` using cluster chasing to successfully load text scripts from USB.

# ANYTHING NEEDED TO REBUILT AND UNDERSTAND THOROUGHLY

**Prerequisites to rebuild:**
1. Rust nightly toolchain with `aarch64-unknown-none` target added (`rustup target add aarch64-unknown-none`).
2. LLVM tools for binary stripping: `rustup component add llvm-tools-preview`.
3. `cargo-binutils` to extract the raw binary: `cargo install cargo-binutils`.
4. Make utility (to run `make all`).

**Steps to run on hardware:**
1. Build using `make`. This will compile and generate `kernel8.img`.
2. Format a MicroSD card to FAT32.
3. Copy standard Raspberry Pi 3 boot files (found in the `BOOT_FILES` directory or the official RPi firmware repo: `bootcode.bin`, `start.elf`, `fixup.dat`).
4. Copy the generated `kernel8.img` to the root of the SD card.
5. Provide power, attach an HDMI display and USB keyboard.

**Resources to thoroughly understand:**
- "Raspberry Pi 3 BCM2837 ARM Peripherals Manual" for MMIO addresses (Mailbox, GPIO, Timers).
- ARM Architecture Reference Manual (ARMv8, for AArch64 exceptions, EL0/EL1 transitions).
- USB 2.0 Specification / DWC2 driver specifics to grasp the `usb/*` subsystem internals.
